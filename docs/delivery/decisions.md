# 决策记录

## DEC-001：治理资料与业务代码分离

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调 / 架构
- 背景：需要引入 UAPD 文件化协作，同时不能干扰小程序、云函数和后台运行。
- 决策：根目录仅保留工具自动发现所需的 `AGENTS.md` 和项目入口 `README.md`；状态、任务、决策、交接、backlog、指标和迭代资料统一放在 `docs/delivery/`；角色配置放在 `.codex/agents/`。
- 替代方案：全部放根目录，查找直接但污染项目入口；混入各业务模块，局部清晰但难以形成全局事实源。
- 影响：不改变运行时、构建和部署路径；需要所有角色使用新的 `docs/delivery/` 路径。

## DEC-002：以产品、体验、架构及前后端角色作为初始角色集

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调
- 决策：配置主协调、前端、后端、QA 四个基础执行角色，并加入产品、UX/UI、架构角色。项目不注册统一实现角色；安全、数据库、DevOps、发布等角色只在真实风险出现时按需增加。
- 原因：覆盖当前产品的发现、体验、跨端架构、实现和质量闭环，同时控制协作成本。
- 影响：小任务可裁剪到主协调 + 前端或后端；跨端任务必须架构先冻结契约，再分别交给前端和后端；支付、隐私、认证、数据迁移等高风险任务必须升级流程。

## DEC-003：以当前实现和可复现证据建立基线

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调 / QA
- 决策：历史 `PRD.md`、`TECH.md` 保留为重要上下文，但与代码冲突时以当前代码、测试和运行证据为准，并记录待校准事项。
- 原因：现有文档包含早期“尚未完成”表述，而仓库已有后续实现和提交。
- 影响：不得依据旧文档删除当前能力；后续由产品与架构角色显式校准差异。

## DEC-004：指标缺失时记录“待采集”而非估算

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：产品
- 决策：`metrics.md` 定义口径、数据源和目标设置流程；在没有生产查询证据前，基线和目标值标记为待采集/待确认。
- 影响：初始化迭代只能评价交付体系和工程基线，不能宣称业务转化改善。

## DEC-005：产品能力采用三级成熟度描述

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：产品 / 架构 / QA
- 决策：文档将能力标为“已实现”“受限实现”或“待验证”。存在代码不等于已生产上线；mock 支付、调用方提供审核信号和未部署验证的外部集成都不能标为完整交付。
- 原因：旧文档把大量现有能力写成未实现，但直接改成“全部完成”又会掩盖真实生产缺口。
- 影响：产品验收和发布闸门必须分别核对代码、测试、目标环境与真实外部服务证据。

## DEC-006：支付与自拍审核是独立的 Level 3 上线工作

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：产品 / 架构
- 决策：订单/解锁状态机保留，但真实微信支付接入必须以可信服务端回调为准；自拍审核结果必须由服务端可信能力产生，不能依赖客户端声明。两项分别建立高风险迭代。
- 影响：完成前不得对外宣称真实付费与审核闭环达到生产准入。

## DEC-007：工作流以项目 Skill 作为唯一编排入口

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调
- 决策：使用 `.agents/skills/product-delivery-workflow/SKILL.md` 作为 UAPD 编排入口，并提供 `agents/openai.yaml`、调用示例和任务包模板；项目事实路径固定为 `docs/delivery/`。
- 原因：角色 TOML 只定义职责，不会自动串起任务分级、阶段闸门、Handoff Contract 和结果闭环；原 Skill 仍是生成器占位模板，无法承担编排。
- 影响：用户可用 `$product-delivery-workflow` 显式启动；技能也可被相关交付请求自动发现。多角色配置不强制并行，是否委派仍受当前运行环境和用户授权约束。

## DEC-008：采用 UAPD 1.4 四维任务分类

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调
- 决策：所有新任务分别记录 Lifecycle、Execution Mode、Task Type 和 Risk Level，不再用单一“运行模式”字段混合表达持续迭代、局部修改和 Bug。
- 原因：生命周期决定如何结束，执行模式决定流程裁剪，任务类型决定变更对象，风险等级决定角色和控制强度；四者不能互相替代。
- 影响：Skill、模板、调用示例、README、主协调角色和有效 Handoff 使用新字段；历史 ITER-001/002 补齐独立 `RETRO.md`，但不重写当时没有产生的生产证据。

## DEC-009：实现职责严格拆分为前端与后端

- 日期：2026-09-12
- 状态：Accepted
- 决策角色：主协调 / 架构
- 决策：下线统一 `implementer` 注册，新增 `frontend` 与 `backend` 两个独立子 Agent。前端拥有小程序和 admin 客户端边界；后端拥有云函数、服务、API、数据和权限边界。跨端任务必须使用两个独立 Handoff Contract。
- 原因：统一实现角色同时修改客户端和服务端，无法保证文件所有权、契约先行和独立 QA 证据。
- 影响：API 或数据变更必须先过架构闸门；前后端可并行但不得重叠文件，QA 分别验证两侧及集成行为。
